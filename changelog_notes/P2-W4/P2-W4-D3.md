### Changelog

#### 1. Extend the existing GitHub Actions CI workflow for container publishing

The existing workflow from P2-W4 D1 and D2 was extended rather than
creating a separate CI workflow.

The workflow remains:

``` text
.github/workflows/ci.yml
```

D2 had already established:

-   GitHub Actions triggers for pushes to `main`
-   Pull-request triggers targeting `main`
-   Python 3.11 setup
-   Repository structure validation
-   Limited automated import tests
-   Unified Docker image build using the canonical root `Dockerfile`

D3 extended that workflow with:

-   GitHub Container Registry permissions
-   GHCR authentication
-   Git commit SHA image tagging
-   GHCR image publishing
-   Separate success messages for CI validation and image publishing

The final D3 workflow is:

``` yaml
name: Weather Intelligence Platform CI

on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main

jobs:
  ci:

    runs-on: ubuntu-latest

    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Verify Python
        run: python --version

      - name: Install limited test dependencies
        run: |
          python -m pip install --upgrade pip
          python -m pip install numpy pandas requests scikit-learn joblib

      - name: Verify repository structure
        run: |
          test -f Dockerfile
          test -d k8
          test -d orchestration
          test -d dags
          test -d w10_fastapi_service

      - name: Run limited tests
        run: python -m unittest tests/test_project_imports.py

      - name: Build unified Docker image
        run: docker build -t weather-platform:ci .

      - name: Log in to GitHub Container Registry
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Tag image with commit SHA
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: |
          docker tag \
            weather-platform:ci \
            ghcr.io/${{ github.repository }}:${{ github.sha }}

      - name: Push versioned image to GHCR
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: |
          docker push \
            ghcr.io/${{ github.repository }}:${{ github.sha }}

      - name: CI validation successful
        run: echo "P2-W4-D3 CI validation completed successfully"

      - name: Image publishing completed
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: echo "P2-W4-D3 container image published successfully"
```

#### 2. Configure GitHub Actions package permissions

The following permissions were added to the `ci` job:

``` yaml
permissions:
  contents: read
  packages: write
```

The existing `contents: read` permission allows the workflow to read the
repository.

The new:

``` yaml
packages: write
```

permission allows the GitHub Actions job to publish the Docker image to
GitHub Container Registry.

This is required for the `docker push` operation used later in the
workflow.

#### 3. Use GitHub Container Registry (GHCR)

GitHub Container Registry was selected as the container registry for the
project.

The target image repository is based on:

``` yaml

```

For this project, the resulting package is:

``` text

```

Using:

``` text

```

instead of hard-coding the repository name keeps the workflow tied to
the repository that triggered it.

The registry is:

``` text
ghcr.io
```

which is GitHub Container Registry.

#### 4. Authenticate GitHub Actions to GHCR

The following step was added:

``` yaml
- name: Log in to GitHub Container Registry
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  uses: docker/login-action@v3
  with:
    registry: ghcr.io
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }}
```

The `if` condition is important:

``` yaml
github.event_name == 'push' && github.ref == 'refs/heads/main'
```

This means the registry login occurs only when the workflow is running
because of a direct push to `main`.

Pull-request validation therefore does not publish an image.

The authentication uses:

``` yaml
password: ${{ secrets.GITHUB_TOKEN }}
```

The GitHub Actions token is supplied by GitHub for the workflow run. A
separate Docker Hub password or manually-created registry token was not
added.

#### 5. Tag the image with the Git commit SHA

The CI build creates a temporary CI image:

``` yaml
- name: Build unified Docker image
  run: docker build -t weather-platform:ci .
```

D3 then creates the registry tag:

``` yaml
- name: Tag image with commit SHA
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  run: |
    docker tag \
      weather-platform:ci \
      ghcr.io/${{ github.repository }}:${{ github.sha }}
```

The important variable is:

``` text
${{ github.sha }}
```

GitHub automatically provides the full commit SHA for the commit that
triggered the workflow.

The user therefore does not have to manually find, copy, or enter the
commit SHA.

For the successful D3 run, the resulting published image tag was:

``` text
5d9218b782bc2441aa392d772304073bfb99b15d
```

The resulting complete image reference is:

``` text
ghcr.io/gaurav-dwivedi-de/data_engineering_portfolio:5d9218b782bc2441aa392d772304073bfb99b15d
```

This provides immutable version identification at the Git commit level.

#### 6. Push the versioned image to GHCR

The following step was added:

``` yaml
- name: Push versioned image to GHCR
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  run: |
    docker push \
      ghcr.io/${{ github.repository }}:${{ github.sha }}
```

The command pushes the image created and SHA-tagged in the previous
steps to GitHub Container Registry.

The registry therefore stores an image associated with the exact source
revision that triggered the build.

The deployment process can later use this exact image reference instead
of relying on the mutable:

``` text
airflow-custom:latest
```

tag.

### Problems / Decisions During D3

#### GHCR selected instead of Docker Hub

GitHub Container Registry was selected because the project is already
hosted on GitHub and GitHub Actions can authenticate to GHCR using the
workflow-provided `GITHUB_TOKEN` with the required package permission.

This avoids adding a separate Docker Hub credential to the project at
this stage.

#### Immutable Git-SHA tagging selected

The project currently uses:

``` text
airflow-custom:latest
```

in local and Oracle Kubernetes deployments.

For CI/CD, relying only on `latest` would make it difficult to identify
exactly which build is running.

D3 therefore uses:

``` text
${{ github.sha }}
```

to create an image tag tied to the source commit.

The verified D3 image is:

``` text
ghcr.io/gaurav-dwivedi-de/data_engineering_portfolio:5d9218b782bc2441aa392d772304073bfb99b15d
```

This provides a direct source-to-image relationship.

#### No Oracle deployment during D3

The GHCR image was intentionally not deployed to Oracle during D3.

The current Oracle workloads continue to use:

``` text
airflow-custom:latest
```

D4 is responsible for establishing the connection between GitHub
Actions, the registry, and Oracle K3s.

#### Local and Oracle Kubernetes are separate clusters

The local environment is:

``` text
Docker Desktop Kubernetes
```

while the cloud environment is:

``` text
Oracle Cloud K3s
```

They are separate Kubernetes clusters.

The same project Kubernetes manifests can be used as deployment
configuration for both environments, but the clusters themselves are
independent.

#### Docker image versus Kubernetes configuration

D3 reinforced the distinction between:

``` text
Docker image
```

and:

``` text
k8/*.yaml
```

The Docker image packages the project's application runtime and required
software.

The Kubernetes manifests define how Kubernetes should run the workloads.

K3s is the platform that manages the resulting pods and containers.

Kubernetes/K3s is therefore not being packaged inside the application
Docker image.

#### `k8/` changes are deployable platform changes

The final target architecture treats changes under:

``` text
k8/
```

as deployable infrastructure/configuration changes.

A future D4 deployment pipeline must therefore recognize `k8/` changes
and propagate them to Oracle K3s.

A new Docker image is not technically required for every Kubernetes YAML
change, but the change still needs to reach the Oracle cluster.
