```yaml
  pull_request:

        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5

      - name: Verify Python

      - name: Verify repository structure

      - name: Build unified Docker image
        run: docker build -t weather-platform:ci .

      - name: CI validation successful
        run: echo "P2-W4-D2 validation passed"
```

#### 2. Python environment and dependency preparation

The workflow uses:

```yaml
- name: Set up Python
  uses: actions/setup-python@v5
  with:
    python-version: "3.11"
```

This gives the GitHub Actions runner the Python version used for the D2 validation environment.

The workflow then installs only the dependencies required by the limited tests:

```yaml
- name: Install limited test dependencies
  run: |
    python -m pip install --upgrade pip
    python -m pip install numpy pandas requests scikit-learn joblib
```

The purpose is to make the small import tests executable without installing the entire project's Docker dependency environment directly into the GitHub Actions Python environment.

The Docker image has its own dependency installation through the canonical root `Dockerfile`.

#### 3. Create the limited test file

A small test file was created at:

```text

```

The test file uses Python's built-in `unittest` framework:

```python
import unittest


class TestProjectImports(unittest.TestCase):

    def test_core_dependencies(self):
        import numpy
        import pandas
        import requests

        self.assertIsNotNone(numpy)
        self.assertIsNotNone(pandas)
        self.assertIsNotNone(requests)

        import joblib

        self.assertIsNotNone(sklearn)
        self.assertIsNotNone(joblib)


if __name__ == "__main__":
    unittest.main()
```

The test was intentionally kept small for the first CI implementation. More comprehensive project tests can be added later.

#### 4. Explanation of the test code

The first line:

```python
import unittest
```

imports Python's built-in testing framework.

This was used instead of adding `pytest` as another project dependency because D2 only requires a small initial validation layer.

The test class:

```python
class TestProjectImports(unittest.TestCase):
```

creates a test class using `unittest`.

The first test:

```python
def test_core_dependencies(self):
    import numpy
    import pandas
    import requests

    self.assertIsNotNone(numpy)
    self.assertIsNotNone(pandas)
    self.assertIsNotNone(requests)
```

checks that three core Python dependencies can be imported successfully:

- NumPy
- Pandas
- Requests

The test does not test application logic. It simply confirms that these packages are available and importable in the CI validation environment.

The second test:

```python
def test_ml_dependencies(self):
    import sklearn
    import joblib

    self.assertIsNotNone(sklearn)
    self.assertIsNotNone(joblib)
```

checks that the main machine-learning dependencies used by the project can be imported:

- Scikit-learn
- Joblib

Again, the purpose is basic environment validation rather than model-performance testing.

The assertions:

```python
self.assertIsNotNone(...)
```

confirm that the imports produced usable module objects.

Finally:

```python
if __name__ == "__main__":
    unittest.main()
```

allows the file to be executed directly through Python's `unittest` runner.

#### 9. Explanation of the Docker build command

The command was:

```bash
docker build -t weather-platform:local .
```

`docker build` tells Docker to build an image using a Dockerfile.

The option:

```text
-t weather-platform:local
```

assigns the resulting image the name:

```text
weather-platform
```

and the tag:

```text
local
```

Together, these identify the local image as:

```text
weather-platform:local
```

The final:

```text
.
```

means the current project directory is used as the Docker build context.

This is important because the root Dockerfile uses project files through `COPY` instructions. The build context makes the required repository files available to Docker.

The `local` tag was used only to identify the image built on the Mac for local validation.

#### 12. Docker availability in GitHub Actions

A separate Docker installation step was not added to the workflow.

The workflow runs on:

```yaml

```

The GitHub-hosted Ubuntu runner provides Docker tooling, so the workflow can execute:

```bash
docker build -t weather-platform:ci .
```

directly.

This is different from the Python dependency installation step. The workflow installs the specific Python packages required by the tests, while Docker is already available on the hosted runner.

#### 13. Why the Docker image is built during D2

The Docker build is used as an additional CI validation layer.

The limited Python tests answer:

```text
Can the required Python modules be imported?
```

The Docker build answers:

```text
Can the project's complete unified runtime image still be constructed from the current repository?
```

This can detect problems that the small import tests cannot detect, such as:

- Dockerfile errors
- missing files referenced by `COPY`
- dependency installation failures
- Java/Spark setup problems
- incorrect project paths
- failures while constructing the unified application environment

The purpose at this stage is therefore validation, not deployment.

#### 14. Important distinction between CI files and the Docker image

The CI workflow:

```text
.github/workflows/ci.yml
```

controls what GitHub Actions does.

The test file:

```text
tests/test_project_imports.py
```

provides the limited automated tests.

The Dockerfile:

```text
Dockerfile
```

defines how the application image is built.

The CI workflow runs the tests and then uses the Dockerfile to build the image.

The CI workflow and test file are not automatically included in the Docker image. The current Dockerfile copies the application and project components required by the unified runtime rather than the GitHub Actions workflow itself.

### Problems / Decisions During D2

#### Limited tests rather than a full test suite

The initial D2 implementation intentionally uses only two import sanity tests.

This keeps the first CI implementation lightweight while establishing an automated testing foundation.

More comprehensive tests can be added later as the project matures.

#### No separate CI Dockerfile

A separate Dockerfile was deliberately not created.

The existing root Dockerfile is the project's canonical unified image definition and is used for both local validation and CI image building.

#### No container registry in D2

The image built by GitHub Actions is only used for CI validation at this stage.

It is not pushed to a registry during D2.

Container registry publishing and immutable image versioning are deferred to P2-W4 D3.

#### No Oracle K3s deployment in D2

The D2 workflow does not deploy the image to Oracle Cloud K3s.

Kubernetes deployment automation is deferred to the later P2-W4 stages.
