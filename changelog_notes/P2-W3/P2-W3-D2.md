# P2-W3 --- Daily Development Notes

## 01/09/2026

### Task

- P2-W3 D2: Configure Kubernetes CPU and memory requests/limits for the Weather Intelligence Platform and resolve resource-scheduling issues on the Oracle Cloud Free Tier VM.

### Changelog

#### 1. Review Kubernetes resource allocation

After the initial cloud deployment, the next task was to make the workloads fit within the limited CPU and memory available on the Oracle Cloud VM.

The K3s node had limited allocatable CPU, so Kubernetes resource requests were important for scheduling.

The deployments were reviewed for CPU and memory requests/limits, particularly:

- PostgreSQL
- MinIO
- Airflow API Server
- Airflow Scheduler
- Airflow DAG Processor
- FastAPI
- Prediction Dashboard

The objective was to prevent a workload from requesting more resources than the node could allocate while still maintaining reasonable resource limits.

**Main Command**

```bash
kubectl describe node weather-platform-k3s
```

This was used to inspect the node's capacity, allocatable resources, current requests and limits.

#### 2. FastAPI pod became Pending

During a FastAPI Deployment restart, the replacement pod remained:

```text
Pending
```

The Kubernetes scheduler reported:

```text
Insufficient cpu
```

The problem was caused by the combined CPU requests of the existing workloads leaving insufficient allocatable CPU for the new FastAPI pod.

The node had only 2 CPUs available, making resource requests particularly important during rolling updates.

#### 3. Reduce the FastAPI CPU request

The FastAPI Deployment originally requested:

```yaml
resources:
  requests:
    cpu: 250m
```

The request was reduced to:

```yaml
resources:
  requests:
    cpu: 100m
```

The CPU limit remained higher so that the application could still use additional CPU when available.

After the change, Kubernetes was able to schedule the replacement FastAPI pod.

The Deployment subsequently converged to:

```text
READY   UP-TO-DATE   AVAILABLE
1/1     1            1
```

#### 4. Verify resource configuration and scheduling

The node and workloads were checked again after the adjustment.

**Main Commands**

```bash
kubectl get pods -o wide

kubectl get deployments

kubectl describe node weather-platform-k3s
```

The FastAPI pod successfully changed from `Pending` to `Running`, confirming that the resource request adjustment resolved the scheduling problem.

### Problems Faced

The main issue was CPU contention during a Deployment rollout.

The Oracle Cloud Free Tier VM had limited CPU capacity, and Kubernetes schedules pods according to their resource **requests**, not simply their actual current CPU usage.

The original FastAPI request of `250m` could not be accommodated alongside the existing workload during the replacement-pod scheduling phase.

Reducing the request to `100m` allowed the pod to schedule while retaining a higher CPU limit for runtime bursts.

### Observations

This task demonstrated an important Kubernetes distinction:

- **Requests** determine the resources Kubernetes reserves for scheduling.
- **Limits** define the maximum resources a container can consume.

On a small cloud VM, unnecessarily high requests can prevent pods from scheduling even when the applications are not actively consuming that much CPU.

The resource configuration therefore had to balance application requirements with the actual capacity of the Oracle VM.

### Final Status

**P2-W3 D2: Complete**

CPU and memory resource configuration was reviewed for the Kubernetes workloads. A FastAPI rollout initially failed to schedule because of insufficient CPU. The FastAPI CPU request was reduced from `250m` to `100m`, after which the replacement pod scheduled successfully and the Deployment returned to `1/1` Ready.
