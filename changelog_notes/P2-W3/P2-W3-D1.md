#### 6. Configure Kubernetes RBAC for Airflow

Because the Airflow DAG needs to refresh the FastAPI and Prediction Dashboard Deployments after new S3 artifacts are generated, Kubernetes RBAC was introduced.

A dedicated ServiceAccount was created:

```text
airflow-scheduler
```

A namespace-scoped Role was created with only the permissions required to access and patch:

```text
fastapi-deployment
prediction-dashboard-deployment
```

The Role was connected to the ServiceAccount through a RoleBinding.

**Main Command**

```bash
kubectl apply -f k8/airflow/rbac.yaml
```

This implements least-privilege access instead of giving the Airflow scheduler unrestricted Kubernetes permissions.

The RBAC configuration allows the Airflow scheduler to authenticate to the Kubernetes API and perform the application refresh operation from inside the cluster.

#### 8. Add automatic application refresh after S3 artifact upload

The Airflow DAG was changed to include a `refresh_applications()` task after the pipeline uploads the latest artifacts to AWS S3.

The FastAPI and Dashboard deployments use init containers to download the required model and data artifacts from S3 when a new pod starts.

Therefore, uploading new artifacts to S3 alone does not update the files already present inside running application pods.

The `refresh_applications()` task was added to solve this synchronization problem.

**Core Code**

```python
apps_v1.patch_namespaced_deployment(
    name=deployment_name,
    namespace="default",
    body={
        "spec": {
            "template": {
                "metadata": {
                    "annotations": {
                        "kubectl.kubernetes.io/restartedAt": timestamp
                    }
                }
            }
        }
    }
)
```

The code patches the Deployment Pod template by changing the `restartedAt` annotation. This causes Kubernetes to create replacement pods through the Deployment's normal rolling-update mechanism.

The newly created pods run their S3 download init containers again and retrieve the latest artifacts before starting FastAPI and the Prediction Dashboard.

The resulting flow is:

```text
Airflow pipeline
      |
      v
Generate latest artifacts
      |
      v
Upload artifacts to AWS S3
      |
      v
refresh_applications()
      |
      +-----------------------+
      |                       |
      v                       v
FastAPI Deployment     Dashboard Deployment
      |                       |
      +-----------+-----------+
                  |
                  v
             New pods
                  |
                  v
        S3 download init container
                  |
                  v
          Latest application
             artifacts
```

This change was necessary to prevent the running applications from continuing to use stale model, feature, prediction and metrics files after a successful pipeline run.

#### 9. Resolve initial deployment configuration problems

The initial deployment exposed several Kubernetes configuration issues.

**Missing Kubernetes Secret**

Several workloads initially reported:

```text
CreateContainerConfigError
```

The underlying issue was that the `weather-env` Secret was not available to the newly deployed workloads.

The Secret was recreated from the VM copy of the project `.env` file:

```bash
kubectl create secret generic weather-env --from-env-file=/home/ubuntu/.env
```

This allowed the workloads that depended on the Secret to start.

**AWS CLI init-container image pull policy**

FastAPI and Dashboard init containers initially reported:

```text
Init:ErrImageNeverPull
```

The AWS CLI init-container image was configured with:

```yaml
image: public.ecr.aws/aws-cli/aws-cli:latest
imagePullPolicy: Never
```

`imagePullPolicy: Never` requires the image to already exist in the K3s node's local containerd image store. The AWS CLI image was not available locally, so Kubernetes could not start the init containers.

The policy was changed to:

```yaml
imagePullPolicy: IfNotPresent
```

This allows K3s to use a local copy when available and otherwise pull the image from the registry.

**CPU resource constraint**

The limited Oracle VM CPU resources later caused a FastAPI replacement pod to remain:

```text
Pending
```

The issue was caused by insufficient allocatable CPU for the pod's requested resources. The FastAPI CPU request was reduced from `250m` to `100m`, allowing the replacement pod to schedule successfully.
