# P2-W3 --- Daily Development Notes

## 03/09/2026

### Task

- P2-W3 D4: Complete Kubernetes Secrets, application networking, AWS S3 integration and external dashboard exposure for the Oracle Cloud deployment.

### Changelog

#### 1. Configure Kubernetes Secrets

The project `.env` file remained outside the Kubernetes manifests and was used to create the Kubernetes Secret consumed by the workloads.

The Secret was recreated on the Oracle VM with:

```bash
kubectl create secret generic weather-env --from-env-file=/home/ubuntu/.env
```

The Secret provided configuration for PostgreSQL, Airflow, MinIO, FastAPI, W10 and AWS/S3 integration without placing the credential values directly into the Deployment manifests.

#### 2. Verify Kubernetes Services and networking

The deployed applications were exposed through Kubernetes Services.

The main services included:

```text
airflow-apiserver              NodePort  8080:30080
fastapi-service                NodePort  8000:30001
postgres                       ClusterIP 5432
prediction-dashboard-service   NodePort  8051:30002
weather-minio                  NodePort  9000:30900, 9001:30901
```

**Main Commands**

```bash
kubectl get svc

kubectl get endpoints
```

PostgreSQL remained internal through a ClusterIP Service, while the application and dashboard services used NodePorts.

#### 3. Verify AWS S3 access from the Oracle VM

AWS CLI was installed on the Oracle VM so that S3 could be verified directly from the cloud environment.

**Command**

```bash
aws --version
```

AWS credentials were loaded into the current shell from the VM copy of `.env` without storing the secret values in the project manifests.

The S3 connection was then tested:

```bash
aws configure list

aws s3 ls
```

The project bucket was accessible:

```text
weather-data-lake-mlops
```

A recursive listing confirmed the expected features, models, metrics and prediction artifacts were available in S3.

#### 4. Verify S3-backed FastAPI and Dashboard startup

FastAPI and the Prediction Dashboard use AWS CLI init containers to download their required artifacts from S3 when their pods start.

The init containers successfully downloaded:

- `best_model.pkl`
- `scaler.pkl`
- `model_metrics.json`
- `w7_features_final.parquet`
- `weather_predictions.csv`

This confirmed the cloud application was using AWS S3 as the artifact source.

#### 5. Configure external dashboard access

The dashboard was exposed through the K3s NodePort and then made publicly reachable using Cloudflare.

The existing Quick Tunnel forwarded:

```text
Cloudflare
   ->
cloudflared
   ->
127.0.0.1:30002
   ->
K3s prediction-dashboard-service
```

The public dashboard was also routed through the Cloudflare Worker:

```text
ml.weather-intelligence.workers.dev
```

The Quick Tunnel was verified with:

```bash
curl -I https://left-demonstrate-lat-optical.trycloudflare.com/
```

The response returned HTTP 200, confirming that the external dashboard path was operational.

#### 6. Investigate permanent Cloudflare Tunnel

A permanent named Cloudflare Tunnel was considered as a replacement for the Quick Tunnel.

`cloudflared tunnel login` was attempted, but the Cloudflare account did not have a normal DNS zone available for the required named-tunnel setup. The existing working Quick Tunnel was therefore retained rather than disrupting the functioning dashboard.

A permanent tunnel remains a later improvement.

### Problems Faced

Several configuration issues were resolved during this stage:

- The Kubernetes `weather-env` Secret initially did not exist after the clean deployment.
- AWS CLI init containers initially used `imagePullPolicy: Never`, producing `Init:ErrImageNeverPull`.
- The dashboard needed pod replacement after new S3 artifacts were uploaded because its init container downloads artifacts only when a pod starts.
- Cloudflare Workers cannot directly access the Oracle VM's `127.0.0.1`; the existing `cloudflared` tunnel was required to bridge the external request to the K3s NodePort.
- The permanent named Cloudflare Tunnel setup could not be completed because the account did not have a normal DNS zone available.

### Observations

This stage connected the Kubernetes platform to external cloud services.

AWS S3 became the persistent artifact store for the ML pipeline, while Kubernetes Secrets provided the runtime configuration. Kubernetes Services provided internal and NodePort networking, and Cloudflare provided external dashboard access without directly exposing the K3s NodePort to the public internet.

### Final Status

**P2-W3 D4: Complete**

Kubernetes Secrets, Services, AWS S3 access and external dashboard exposure were successfully configured and verified. The existing Cloudflare Quick Tunnel remained operational, while permanent Cloudflare Tunnel configuration was deferred as a later improvement.
